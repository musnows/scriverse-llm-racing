# Scriverse Benchmark Review

对用户明确指定的候选 worktree 原样验收，为需求 JSON 中每个测试用例给出可复现结论。

## 确定范围

1. 获取用户明确提供的候选 worktree 目录和分支名，以及需求 ID 或需求 JSON 路径。缺少具体 worktree 目录或分支时先询问；禁止枚举、搜索或读取其他 worktree 和无关分支来猜测目标。
2. 从排行榜仓库的 `web/source/requirements/<requirement-id>.json` 读取 `prompt`、`baseCommit`、`testCases` 和 `scoring`。需求文件是本次验收口径，不用其他需求的规则补充或替换。
3. 完整读取排行榜仓库、候选 worktree 及相关子目录中的 `AGENTS.md`。发生冲突时遵循作用域更具体的规则和用户本轮明确要求。
4. 默认 review 是严格只读：不得修改候选代码、替模型修复问题、创建提交、推送分支或改排行榜。只有用户明确要求记录、上传或发布结果时，才进入写回流程。

## 保护候选结果

- 只在用户点名的 worktree 中执行命令，只读取该候选分支和需求声明的 `baseCommit`。不得借 `git log`、`git diff`、`git show` 或文件搜索读取其他候选分支。
- 开始时记录 `git status --short`、当前分支、HEAD、`baseCommit` 和 merge-base。merge-base 不等于需求基线、分支不符或工作区有未提交改动时，停止评分并说明原因，不得自行纳入、丢弃或修复这些改动。
- 需要验证排行榜链接时，仅查询用户指定的精确远端 ref，例如 `git ls-remote --heads origin refs/heads/worktree/<hash>`，不得枚举所有候选分支。
- 测试生成物只能进入明确的隔离目录、临时目录或项目已有的忽略目录。不得写入候选 worktree 的真实 `.data`，不得读取或影响用户正在使用的 Scriverse/Desktop 实例。
- 完成后再次确认候选 worktree 干净，并清理本次创建的服务、临时数据和测试文件。使用仓库允许的可恢复清理方式，禁止扩大清理范围。

## 独立复审

具备 sub-agent 能力时，默认派发一个独立 reviewer 负责完整 diff、代码安全和自动化测试证据；主 agent 独立负责真实运行、数据库和浏览器验收，并复现 sub-agent 的关键失败。不要把预期答案、怀疑的缺陷或计划判分提前告诉独立 reviewer。用户明确禁止 delegation 时由主 agent 完成两类检查，并在报告中说明没有独立复审。

sub-agent 与主 agent 都必须保持只读。两者结论冲突时，以可重复运行的直接证据为准；必要时补充最小复现，不以多数意见决定结果。

## 逐项判定

为每个 `testCases[]` 条目建立内部矩阵，至少记录测试用例 ID、优先级、验证方式、证据和 `pass`、`fail` 或 `unverified` 状态。

- 逐条验证，不从整体印象、测试总数或代码数量推断通过。
- `fail` 必须有直接代码路径、命令输出、数据库结果、协议记录或真实浏览器行为作为证据，并说明复现前提及可见影响。
- 一个根因使多个测试用例的场景分别失败时，每个失败用例都要记录；同时避免把根因无关的相邻用例机械判失败。
- 扣分为零的 P2 失败仍必须记录，并计入失败数。
- 无法验证时标为 `unverified`，说明缺少的条件。先尝试安全的本地 stub、隔离 fixture 或确定性复现；仍无法判定时不得悄悄算作通过，也不得发布成最终结果。
- 结果数据只记录 `failures` 中实际失败的测试用例 ID 和原因。禁止持久化人工分数、扣分明细、豁免列表或排名；展示分数由平台依据当前 `scoring` 自动计算。用户询问分数时可以按当前规则解释计算过程，但仍不把计算值写入结果 JSON。
- 不根据得分、排名或个人判断设置 `finalAdoptedModelId` 或 `finalAdoptedPrUrl`；这两个字段只接受用户明确指定。

## 验证证据

按需求涉及的能力选择检查，但不能只跑候选新增的测试。

### 代码与自动化测试

- 审查 `baseCommit...HEAD` 的完整 diff、提交边界和提交信息，重点检查正确性、回归、安全、权限、事务、迁移、凭证、文件和网络边界。
- 先跑直接相关测试，再跑项目要求的类型检查、全量测试和生产构建。缺少本地依赖时按项目规则安装后继续，不把 `command not found` 当成候选缺陷。
- 记录命令、通过/失败数量和失败原因；绿色单元测试不能覆盖真实协议或运行时行为时，继续做直接复现。

### 数据库与恢复

- 使用排行榜 `data/` 中与当前需求匹配的公开 fixture；始终复制到隔离目录后运行，禁止原地迁移或写入归档源。
- 迁移前后记录关键表计数，检查备份范围，并运行 `PRAGMA integrity_check` 与 `PRAGMA foreign_key_check`。
- 对备份、导入、恢复或加密功能，实际打开产物并检查数据与凭证恢复链路；文件存在不等于恢复成功。

### 真实运行与浏览器

- 涉及端口时使用 `tmux` 启动，端口必须大于等于 10000；自动探测空闲端口。Scriverse 开发服务使用隔离 `DATA_DIR`、`NODE_ENV=development` 和 `APP_DEV_SKIP_AUTH=true`，并确认健康接口、版本、进程目录和数据库路径属于当前候选。
- 前端变更必须用内置浏览器执行真实交互。按候选 `AGENTS.md` 要求覆盖桌面和窄屏视口，检查入口、主要路径、键盘与焦点、计算样式、横向溢出、遮挡、控制台错误和失败请求。截图是证据补充，不替代行为断言。
- 认证、权限或重启场景不能仅依赖开发跳过登录模式；使用隔离认证数据或已有自动化测试验证真实 401、403、CSRF、角色和会话恢复路径。

### 真实规模与失败注入

- 不把小型内存 mock 当成大文件、流式请求、分页、并发、定时器或第三方协议的最终证据。使用接近公开 fixture 的文件大小、对象数量和持续时间测试关键路径。
- 外部服务优先使用只监听本机的最小兼容 stub，记录服务端实际收到的 method、path、headers 和对象；不得使用真实密钥。验证成功、超时、错误响应、重定向、分页、重复对象和部分失败。
- 当客户端 SDK 与自定义传输层组合时，检查 SDK 最终生成的请求，而不只检查调用参数；确认大 body、流、签名头和条件头能被真实运行时发送。
- 定时任务要求具体等待时间时，应实际按该时间触发一次，同时用确定性测试验证跨日、重启和重复初始化。等待期间继续完成其他审查，不用长时间阻塞命令。
- 日志、Toast、API 和审计中的脱敏要用当前目标的实际测试凭证做反射测试，并覆盖 URL、JSON、XML/HTML 实体和长响应分块；可还原的编码形式仍视为泄漏。

## 报告格式

先给最终失败测试用例集合，不先用大段过程铺垫。报告至少包含：

- 候选分支、基线、HEAD、提交数量和初始/最终工作区状态。
- 每个失败 TC 的复现条件、直接证据、影响和精确文件行号。
- 通过与未验证的 TC 列表；未验证项必须说明阻塞。
- 定向测试、全量测试、构建、数据库和浏览器结果。
- sub-agent 的独立结论及与主 agent 的差异。
- 远端分支是否存在，以及写回排行榜前仍缺少的模型、耗时或用量信息。

不要因为自动化测试全绿而隐藏真实运行失败，也不要因为发现一个严重根因而省略其他测试用例的独立结论。

## 写回排行榜

仅当用户明确要求记录、上传或发布本次结果时，读取并执行 [references/result-publication.md](references/result-publication.md)。普通 review 到报告完成即停止。
