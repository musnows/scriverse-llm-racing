# Scriverse Benchmark Design

将真实产品需求转化为可实现、可评分、且不靠猜题取胜的 LLM benchmark。

## 工作流程

1. 先判断需求来源，再读取当前项目的 `AGENTS.md`、已有功能和用户已确认的需求。
   - **用户已给需求**：将用户给出的能力、边界和优先级视为权威输入。只帮助补全为可复制 prompt、功能 case 和评分规则；不要自行更换题目、引入新的产品方向或把个人偏好写成验收条件。
   - **用户要求想需求**：仅在用户明确表示不知道做什么、要求构思新需求或要求给出候选题目时，才从 Scriverse 创作工作台主线中提出 2–3 个真实候选需求。说明各自的用户价值和复杂度，将推荐项放在第一位，但由用户选择或确认后再写成完整 benchmark prompt。若用户明确要求“直接给一题”，可输出一个标明为候选的完整题目。
2. 在用户已确认题目后，提高难度时优先增加同一能力链路中的持久化状态、权限交集、事务、版本、幂等、审计和恢复，而不是叠加无关页面或格式。
3. 输出可复制的中文需求 prompt。明确用户可见行为、权限边界、数据生命周期、失败状态和不支持的能力；不要要求实现者自行测试、提供截图或适配移动端，除非用户明确要求这些交付流程。若当前项目 `AGENTS.md` 要求独立 Git commit 或 Angular Commit 格式，必须将其保留为独立交付门槛。
4. 输出验收用例时使用三列表格，表头必须逐字为：`case id`、`优先级`、`desc`；不要使用 `TC-xx`、`priority` 等替代表头。编号写为大写 `TC-01`，并保持已有编号稳定；不为凑数加入不能从需求或 `AGENTS.md` 推出的要求。
5. 将 P00 留给权限绕过、未确认写入、跨作品数据泄露、认证或正文误写等发布阻断问题；P0 覆盖核心用户功能；P1 覆盖持久化、版本和次级完整性；P2 仅放不扣分的低风险边缘行为。
6. 用户要求 200 分制且希望最低保留 20 分时，先统计各优先级用例数量，再选择扣分值使最大扣分不超过 180。不要复用不匹配当前用例数量的旧权重。

## 设计约束

- 只对产品代码行为评分。测试执行、截图、浏览器验收和移动端适配属于评审或交付流程，不能混入功能分，除非用户明确将它们纳入题目。Git commit 是代码交付逻辑：当前项目 `AGENTS.md` 有提交要求时，必须将其作为独立交付门槛保留；只有用户明确要求时才把它计入功能评分。
- 公开需求可以直接验证；将权限撤销、重放、跨作品、并发确认等具体场景作为隐藏评测数据，而不是塞进 prompt 的实现说明。
- 不把接口名、数据库表名、响应码或实现算法强加给实现者，除非这些本身是产品契约。
- 将用户纠正后的决定视为最高优先级，并同步更新 prompt、TC 和评分规则，避免旧版本残留。
- 使用中文沟通和中文需求文字；新增说明中不要使用 emoji。
