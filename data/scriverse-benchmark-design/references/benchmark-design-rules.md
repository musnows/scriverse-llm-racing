# Benchmark 设计规则

## 用户已确认的输出偏好

- 默认用中文。
- 需求必须像真实产品迭代，优先贴合 Scriverse 的创作、协作、权限、版本和本地数据管理主线。
- 当用户要求提高难度时，增加同一能力链路中的状态、权限、并发、事务、恢复和审计；不要为了难度加入不相关功能。
- 需求 prompt 只描述产品代码功能。不要把“运行测试”“截图”“浏览器验收”或“移动端适配”写成被测 AI 的功能要求，除非用户明确要求。若项目 `AGENTS.md` 规定独立 Git commit 或 Angular Commit 格式，必须把它保留为独立交付门槛。
- TC 表固定为 `case id | 优先级 | desc`，ID 使用大写 `TC-01` 格式。
- 如果已有 TC 编号，修改内容时保持编号不变；删除后保留空缺，新 case 使用新编号。
- 20 条高质量功能 case 优于 25 条填充 case。

## 需求来源模式

### 用户已给需求

- 用户选择需求，AI 不替用户换题或擅自决定产品方向。
- 先复述已知边界，必要时检查项目现状，再把该需求扩展为完整 prompt、TC 和评分。
- 只纳入用户明确提出、用户在后续纠正中确认，或 `AGENTS.md` 直接要求的行为。

### 用户要求想需求

- 只有用户明确表示“不知道做什么”“帮我想一个需求”“给我出题”时，AI 才提出候选需求。
- 候选必须与 Scriverse 的创作、协作、权限、版本或本地数据管理主线有关；避免为了复杂度拼接无关功能。
- 先给 2–3 个候选，推荐项放在第一位并说明复杂度和用户价值；用户选择或确认后才将其视为正式需求。
- 用户明确要求直接给出一题时，可以输出一个完整候选 prompt，但必须表明它仍是提案而非用户已确认的产品决定。

## 用例来源规则

- 用例只能来自用户明确的需求、当前项目 `AGENTS.md`，或两者直接必然推出的可观察行为。
- 不把个人偏好伪装成需求。例如“每种实体必须独立开关”“选项必须去重”“AI 摘要必须写入审计”“推荐项不得默认选中”，除非用户明确提出。
- 可以为“禁止任何形式越权”“必须确认后写入”“作品级权限”等明确原则设计对抗场景，但不要在公开 prompt 中泄露具体攻击步骤。
- 将测试、截图和响应式检查作为评审侧动作；功能 TC 只描述软件应呈现的结果。Git commit 是代码交付的一部分：按当前项目 `AGENTS.md` 保留为独立交付门槛，除非用户明确要求，否则不与功能 TC 的产品分混算。

## 优先级含义

| 优先级 | 含义 |
|---|---|
| P00 | 权限绕过、未确认写入、认证或同源保护失效、跨作品泄露、正文被错误改写等阻断问题。 |
| P0 | 用户承诺的核心功能不可用、确认内容不正确、范围或数据写错。 |
| P1 | 持久化、版本、审计、恢复、配置边界等重要完整性问题。 |
| P2 | 不影响分数的低风险边缘行为。 |

## 200 分评分模板

先根据当前 case 数量计算，不要机械沿用旧分值。

当前“持久化审批工作流”基线有 9 条 P00、7 条 P0、3 条 P1 和 1 条 P2。为保留 20 分，可使用：

| 优先级 | 每条不通过的扣分 |
|---|---:|
| P00 | -14 分 |
| P0 | -6 分 |
| P1 | -4 分 |
| P2 | 0 分 |

最大扣分为 `9 × 14 + 7 × 6 + 3 × 4 = 180`，最低保留 20 分。

## 复杂度升级模式

将简单“AI 工具调用 + toast 确认”升级为难题时，优先采用以下模式：

1. 将临时确认升级为持久化的审批状态机。
2. 将单项写入升级为有限数量的原子修改计划。
3. 在执行时重新校验工具开关、当前用户、对话归属用户、对象归属和版本。
4. 将重复确认、重试、并发标签页和服务恢复视为同一审批的幂等执行。
5. 将已完成的实体编辑接入版本、审计和受版本约束的撤销能力。
